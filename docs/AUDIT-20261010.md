# Comprehensive release audit, 10 October 2026

The audit found reproducible defects after the earlier implementation checks. The fixes below supersede those earlier checks for these boundaries. Automated fixtures establish implementation behavior; they do not establish a real GitHub App authorization, a holder's browser acceptance or external alert delivery.

## Findings and corrections

| Finding | Correction and verification |
| --- | --- |
| Valid GitHub installation and release responses were rejected when optional fields were absent. | Accept an absent installation client ID while validating any supplied ID, and an absent or null release body. Keep App identity and read-only permission checks. Provider regressions cover the documented response shapes. |
| A rejected newly issued token could remain valid at GitHub. | Attempt revocation for every validation failure after receiving a syntactically valid token. Tests distinguish local rejection from successful remote revocation. |
| Logout or maintenance could occur while callback storage waited for its atomic commit. | Recheck scope, session and execution permission immediately before replacing the encrypted credential. Queued callback, ownership-transfer and maintenance regressions preserve the old credential and revoke the rejected new token. |
| Logout after retrieval could still reach the model, and invalidation while saving could strand a completed result and job capacity. | Recheck authority before the runner and on every actual receipt-rename attempt. Save a terminal failed receipt without answer text when the grant or authority is invalidated. Preserve retryable storage failures. Application regressions prove zero model calls at the pre-run boundary and released capacity after failed commit. |
| Repository listing could make follow-on private requests after disconnect if provider revocation failed. | Register scoped listing cancellation before asynchronous checks, abort after the durable disconnect tombstone, and recheck authority before each provider request. Held-response tests prove no subsequent private request after disconnect or logout. |
| Incomplete inbound requests could stall maintenance or shutdown, including routes returning an early 401 or 405. | Start a 15-second inbound-body deadline at the HTTP boundary. Reject a body reader attached after the request was destroyed. Raw-socket tests cover public challenge, both early responses and authentication spanning the deadline. |
| An uncertain task admission in one form still allowed a second task from another form. | Share the uncertainty guard across chat, public research and GitHub forms. Require explicit Activity review before preparing a separately authorized run; never replay the original POST. Known 400 rejection remains directly retryable. Browser tests cover all three directions, including programmatic submission. |
| GitHub refresh, stale generation and authorization navigation could lose useful state or retain obsolete selection. | Add visible repository refresh and unavailable-state Disconnect, reconcile typed stale-generation conflicts through GET, clear obsolete repository selection and consent, and preserve only the scoped question briefly across authorization. Delayed-navigation checks cover one-time restoration. |
| Consent and accessibility state did not consistently follow field edits or inspector changes. | Clear public-reader consent when question/URLs change, label the composer and GitHub fields, and synchronize inspector expansion on Escape/resize. Browser checks cover the revised controls. |
| A failed recovery alert could be retried during a new unhealthy observation. | Retry recovery only on a healthy observation. The adversarial failure/recovery sequence is covered in monitor tests. |
| Windows backup restore inherited broad parent access before writing plaintext. | Restrict the new restore root to the current user before plaintext extraction. Shared restore code covers both CLI and recurring recovery; real Windows ACL tests preserve the parent ACL and check descendants. |
| Release documents mixed historical source pins with current deployment claims. | Reconcile operations and release docs, preserve dated proof scope, and refresh final deployment/archive receipts separately. Production's existing free-pass setting is reported accurately. |

GitHub response requirements were checked against the official [installation API](https://docs.github.com/en/rest/apps/installations?apiVersion=2026-03-10) and [REST schema](https://github.com/github/rest-api-description/blob/main/descriptions/api.github.com/api.github.com.json). Expiring-token setup is documented in [the connector contract](GITHUB-CONNECTOR.md).

## Verification and release evidence

The frozen revision, final whole-suite result, browser reports, staging public/container hashes, verification-key revocation, monitor observation and archive SHA256 are recorded in the delivery's `comprehensive-audit-20261010.json` and `source-operations-manifest.json`. The local whole-suite log is `evidence/full-audit-final-tests-20261010.log`. Earlier test counts remain evidence for their named revisions only.

The first frozen whole-suite run passed 468 of 469 tests. Instrumentation showed that the maintenance integration fixture's artificial one-millisecond disk polling could repeatedly lock its Windows rename, including every bounded retry. The fixture now uses the actual production receipt persister and default 100-millisecond polling, retaining its held-save, stale-read, authorization and drain assertions. Both direct and production-persistence controls pass at the production cadence. No production timeout or persistence policy was relaxed; the original failure log and the corrected final run are retained separately.

Configured GitHub browser tests use intercepted provider routes and disposable signed fixture sessions. General browser tests use the actual local application persistence with a simulated model. Existing Railway real-provider reader proofs are isolated operator runs and remain separate from holder acceptance. No real GitHub authorization or remote revocation is claimed.
